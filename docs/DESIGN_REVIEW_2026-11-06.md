# CanvaCraft 설계 검토서 — 개발 계획 보강 사항

작성일: 2026-11-06

검토 대상: `docs/DEVELOPMENT_PLAN.md` (2026-11-06, 구현 전 설계안)

상태: 설계 문서만 읽고 작성한 검토서다. 코드 실행, 브라우저 시험, PowerPoint 출력 확인은 하지 않았다. 원본 설계 문서는 수정하지 않았다.

## 1. 검토 결과 요약

원본 설계의 뼈대는 그대로 쓴다. 문서 상태를 바꾸는 곳을 하나로 정한 것, 내보내기를 변경 불가능한 스냅샷에서 수행하는 것, 편집용 PPTX가 어려울 때 이미지 PPTX로 몰래 바꾸지 않는 것, 실제 PowerPoint에서 열어 보기 전에는 완료로 적지 않는 것은 유지한다.

보강할 곳은 19건이다. 7건은 Phase 1 계약을 확정하기 전에 문서에 넣어야 하고, 8건은 해당 Phase를 시작하기 전에 넣으면 된다. 4건은 사용자 결정이나 Phase 2 측정이 있어야 정할 수 있는 항목이었다.

사용자 결정이 필요했던 네 가지는 2026-11-06에 정해졌다. 결정 내용은 §5의 각 항목과 §7에 적었다. 이모지와 iPad 사진 형식(보강 19의 일부)만 Phase 2 측정으로 정할 항목으로 남아 있다.

## 2. 검토 범위와 판단 기준

### 판단 표시의 뜻

| 판단 | 이 문서에서의 뜻 |
|---|---|
| 필수 수정 | Phase 1에서 계약 문서(`docs/contracts.md` 등)를 확정하기 전에 반영한다. 나중에 넣으면 데이터 형식이나 담당 구분을 다시 바꿔야 한다. |
| 계획 수정 | 해당 Phase를 시작하기 전에 완료 기준이나 계약에 넣는다. |
| 확인 후 결정 | 사용자 결정 또는 Phase 2 측정 결과가 있어야 정할 수 있다. 무엇을 확인하면 되는지 항목마다 적었다. |

### 근거의 종류

이 검토서의 주장은 근거가 세 종류다. 섞어 읽지 않도록 구분한다.

- **설계 문서에서 확인됨**: 원본 설계에 규칙이 없거나 두 문장이 서로 맞지 않는다는 지적. 문서를 읽으면 바로 확인된다.
- **공식 문서에서 확인됨**: 2026-11-06에 각 라이브러리의 공식 문서와 릴리스 페이지를 읽어 확인한 내용. 설치해서 실행한 결과는 아니다. 릴리스 페이지에는 연도가 표시되지 않아 버전 번호만 인용한다.
- **Phase 2 확인 필요**: 브라우저·PowerPoint의 실제 동작에 대한 내용. 이 검토서에서는 실행하지 않았으므로 Phase 2에서 측정해야 한다. 본문에 따로 표시했다.

검토하지 않은 범위: 추정 일정의 타당성, 제공 배경·글꼴의 개별 사용 조건, 배포 위치.

## 3. Phase 1 계약 확정 전에 반영할 항목

### 보강 01. 글씨를 줄로 나누는 기준이 정해져 있지 않음

**현재 설계.** §4는 글씨 입력을 "캔버스 위 HTML textarea"로 처리한다. §5의 TextElement는 width와 height를 함께 저장한다. 줄바꿈은 §5에서 "실제 줄바꿈과 폰트 메트릭은 별도 검증한다"로만 적혀 있다.

**문제.** 같은 글을 줄로 나누는 주체가 세 곳이다. 편집 중에는 브라우저의 textarea가 나누고, 편집이 끝나면 Konva의 글씨 요소가 나누고, PPTX를 열면 PowerPoint가 나눈다. 세 곳의 규칙이 서로 다른데 어느 것이 기준인지 정해져 있지 않다. 아래 두 가지도 비어 있다.

- 글씨 상자의 height를 사용자가 정하는지, 줄 수에서 계산하는지.
- 글씨 상자의 모서리를 끌면 폭이 바뀌는지 글씨 크기가 바뀌는지. Phase 6은 "크기 변경"이라고만 적었다.

**영향.**

- 편집을 시작하거나 끝내는 순간 줄이 바뀌어 글자가 한 줄 위아래로 튄다.
- 저장된 height와 실제 줄 수가 달라져 선택 테두리와 이동 범위 제한이 실제 글씨와 어긋난다.
- PPTX에서 줄이 하나 늘면 글씨가 아래 요소와 겹친다. §10은 줄바꿈·겹침 오류를 필수 수정으로 판정하므로 Phase 9 완료 기준을 통과하지 못한다.

**수정안.**

1. 줄 나누기는 앱의 함수 하나가 담당한다. 예: `layoutText(text, style, width)`가 줄 목록과 전체 높이를 돌려준다. 화면 캔버스, 왼쪽 미리보기, PDF, 이미지 PPTX는 모두 이 결과대로 그린다. Konva의 자동 줄바꿈은 끄고 줄 목록을 그대로 넘긴다.
2. TextElement가 저장하는 값은 x, y, width와 글꼴 속성이다. height는 저장하지 않고 `layoutText` 결과로 계산한다. 계산값을 문서에 함께 저장하면 원본이 둘이 되어 "상태를 바꾸는 곳은 하나"라는 §5 원칙과 맞지 않는다.
3. 크기 조절 규칙을 정한다. 좌우 손잡이는 폭을 바꾸고 줄을 다시 나눈다. 모서리 손잡이는 글씨 크기와 폭을 같은 비율로 바꾼다. 높이만 바꾸는 손잡이는 두지 않는다.
4. 편집 중 textarea에는 같은 폭·글꼴·줄 간격을 적용한다. 그래도 줄 위치가 달라지는지 Phase 2에서 측정한다. 달라지면 `layoutText`가 브라우저 DOM의 줄 위치를 측정해 쓰는 방식과 비교해 하나를 고른다.
5. PPTX의 줄바꿈 방식은 Phase 2에서 아래 두 안을 같은 문장으로 비교해 정한다.

| 안 | 방법 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| 가 | PowerPoint의 자동 줄바꿈에 맡긴다 | PowerPoint에서 글을 고치면 자연스럽게 다시 줄이 나뉜다 | 앱과 줄 수가 달라질 수 있다 |
| 나 | 앱이 정한 줄 끝마다 줄바꿈 문자를 넣고 자동 줄바꿈을 끈다 | 줄 수가 앱과 같다 | PowerPoint에서 글을 길게 고치면 줄이 자동으로 나뉘지 않아 글이 상자 밖으로 나간다 |

PptxGenJS 글씨 옵션에 `wrap`(자동 줄바꿈 켜기·끄기)과 `softBreakBefore`(Shift+Enter 줄바꿈)가 있는 것은 공식 문서에서 확인했다. 실제 줄 위치가 얼마나 다른지는 Phase 2 확인이 필요하다.

**검증 방법.** 시험 문장을 고정한다: 띄어쓰기 없는 긴 한글, 한글·영문 혼합, 숫자와 문장부호가 줄 끝에 오는 문장, 이모지가 든 문장. 각 문장에 대해 편집 직전·편집 중·편집 직후의 줄 목록이 같은지 브라우저 테스트로 확인한다. 줄이 달라지는 문장이 하나라도 있으면 실패다. PPTX는 실제 PowerPoint에서 줄 수를 세어 가·나 안을 비교한다.

**최종 판단.** 필수 수정. TextElement의 저장 필드와 `renderSlide`·`exportPptx` 계약이 이 결정에 따라 달라지므로 Phase 1에서 정해야 한다.

### 보강 02. 글꼴을 어디서 가져오고 언제 그리는지 규칙이 없음

**현재 설계.** §2는 "글꼴 선택"을 포함 기능으로 둔다. §7은 받는 PC에 글꼴이 없으면 모양이 달라진다는 점과 Phase 2에서 한글 글꼴을 확정한다는 점을 적었다. 앱 화면이 쓰는 글꼴의 출처와 로딩 규칙은 없다.

**문제.**

- 기기에 설치된 글꼴을 이름으로만 지정하면 같은 작품이 Windows, iPad, 크롬북에서 다른 글꼴로 그려진다. 원본 파일을 다른 기기로 옮겨 재편집한다는 §4의 목적과 맞지 않는다.
- 한글 웹폰트는 보통 글자 범위별로 수십 개 이상의 파일로 나뉘어 필요한 조각만 내려받는다. 캔버스는 글꼴 조각이 늦게 도착해도 스스로 다시 그리지 않는다. 그 사이에 그린 글자는 대체 글꼴로 남는다.
- 글꼴에 굵은 굵기가 따로 없으면 브라우저와 PowerPoint가 각자 다른 방식으로 굵게 흉내 낸다.
- 글꼴을 외부 서비스에서 불러오면 어린이가 쓰는 앱에서 제3자 서버로 요청이 나간다(보강 06과 연결).

**영향.** 글꼴이 달라지면 글자 폭이 달라지고, 보강 01의 줄 나누기 결과가 기기마다 달라진다. 내보내기 직전에 글꼴 조각이 빠져 있으면 PDF에 대체 글꼴이 섞여 나온다.

**수정안.**

1. 앱이 제공하는 글꼴은 재배포가 허용된 글꼴만 고르고, 앱과 같은 주소에서 직접 제공한다. 글꼴 이름·제공 파일·사용 조건을 `docs/asset-licenses.md`에 기록한다.
2. 글꼴 목록은 고정 목록으로 관리한다. TextElement의 fontFamily는 이 목록의 식별자만 허용한다(보강 05의 값 검사에 사용).
3. "굵게"는 실제 굵은 굵기 파일이 있는 글꼴에서만 켤 수 있게 한다. 굵기가 하나뿐인 글꼴을 넣을지는 Phase 2에서 정한다.
4. 글씨를 그리기 전에 `document.fonts.load(글꼴, 실제 글 내용)`으로 그 글에 필요한 조각까지 불러온 뒤 그린다. 글이 바뀔 때, 작품을 열 때, 내보내기 전에 같은 절차를 거친다. §7의 "폰트·사진 로딩 확인"을 이 절차로 구체화한다.
5. PPTX에 적을 글꼴 이름은 Phase 2에서 아래 표를 채워 정한다. PptxGenJS 글씨 옵션 문서에 글꼴 파일을 PPTX에 넣는 기능은 나와 있지 않다(공식 문서에서 확인됨).

| 측정 항목 | 측정 조건 |
|---|---|
| 앱 화면과 PowerPoint의 줄 수·글자 폭 차이 | 받는 PC에 해당 글꼴이 설치된 경우 |
| 같은 차이 | 글꼴이 없어 PowerPoint가 대체 글꼴을 쓴 경우 |
| 대체 글꼴 이름 | Windows 기본 설치 상태 |

1차 지원 환경이 Windows이므로 Windows 기본 글꼴(맑은 고딕)을 PPTX 쪽 기본값으로 쓰는 안도 Phase 2 비교 대상에 넣는다. 이 경우 Windows가 아닌 기기에서는 앱 화면이 다른 글꼴로 그려지므로 1번 규칙과 어느 쪽을 우선할지 결정이 필요하다.

**검증 방법.** 네트워크 속도를 느리게 제한한 브라우저에서 작품을 열고, 모든 글자가 지정 글꼴로 그려진 뒤에만 화면과 출력 이미지가 만들어지는지 확인한다. 처음 쓰는 글자(예: 잘 쓰지 않는 한글 음절)를 입력했을 때 대체 글꼴로 남지 않는지 본다.

**최종 판단.** 필수 수정. 글꼴 목록과 식별자는 문서 형식의 일부이고, 보강 01의 줄 나누기가 글꼴에 의존한다.

### 보강 03. 되돌리기 때 revision 번호 규칙이 없음

**현재 설계.** §5는 `dispatch(command)`가 "새 revision"을 만든다고 적었다. §6은 "완료된 revision이 현재 revision과 같을 때만 저장됨으로 표시"한다. 되돌리기와 다시 실행이 revision을 어떻게 바꾸는지는 없다.

**문제.** 되돌리기가 번호를 이전 값으로 되돌리도록 구현되면 같은 번호가 서로 다른 내용을 가리키게 된다.

1. revision 7의 저장이 시작된다.
2. 사용자가 되돌리기를 눌러 revision 6이 된다.
3. 새로 편집해 다시 revision 7이 된다. 내용은 1번의 7과 다르다.
4. 1번 저장이 끝난다. 완료된 7과 현재 7이 같으므로 "저장됨"이 표시된다.

**영향.** 화면은 "저장됨"인데 실제로 저장된 것은 이전 내용이다. 이 상태에서 탭을 닫으면 마지막 편집이 사라진다.

**수정안.** 계약에 한 줄을 넣는다: revision은 문서 내용이 바뀔 때마다 1씩 커지고, 되돌리기와 다시 실행도 새 번호를 받는다. 한 번 쓴 번호는 다시 쓰지 않는다. 작품을 다시 열면 저장된 번호에서 이어 간다.

**검증 방법.** 저장을 인위적으로 지연시킨 단위 테스트에서 위 1~4 순서를 재현한다. 4번 시점의 저장 상태가 "변경 있음"이면 통과다.

**최종 판단.** 필수 수정. 계약 한 줄로 막을 수 있고, 빠지면 저장 표시를 믿을 수 없다.

### 보강 04. 편집 기능에 필요한 명령을 누가 추가하는지 비어 있음

**현재 설계.** §9의 소유권 표는 `src/commands/`를 Codex가 작성한다. Phase 4~7의 편집 기능(슬라이드 관리, 사진, 글씨, 손그림)은 Claude가 구현한다. Phase 3에서 Codex가 만드는 것은 "명령 처리"다.

**문제.** 획 추가, 글씨 수정, 배경 변경 같은 개별 명령을 Phase 3에서 모두 만드는지, 각 Phase에서 필요할 때 만드는지 적혀 있지 않다. 뒤쪽이라면 Claude가 기능을 만들 때마다 Codex의 명령 추가를 기다리거나, Claude가 Codex 소유 경로를 수정해야 한다.

협업 절차도 전제 하나가 빠져 있다. §9는 브랜치와 worktree를 쓰는데, 현재 폴더는 git 저장소가 아니다(작업 환경에서 확인됨).

**영향.** Phase 4~7이 기능 단위로 멈추거나, 같은 파일을 두 에이전트가 고쳐 §9의 "같은 파일 동시 수정 금지"가 깨진다.

**수정안.**

1. Phase 1 계약에 첫 버전의 전체 명령 목록을 적는다(이름, 입력, 실패 조건, 취소 단위).
2. Phase 3 완료 기준에 "계약의 모든 명령이 테스트와 함께 제공됨"을 추가한다. Claude는 Phase 4부터 이 명령을 호출만 한다.
3. Phase 4 이후 명령이 더 필요하면 `docs/contracts.md`를 먼저 고치고 Codex가 구현한다. 이 경로를 작업 요청 양식에 적는다.
4. Phase 1 산출물에 git 저장소 생성과 기준 커밋을 추가한다.

**검증 방법.** Phase 3 종료 시 계약의 명령 목록과 테스트 목록을 일대일로 대조한다. 테스트가 없는 명령이 있으면 Phase 4로 넘어가지 않는다.

**최종 판단.** 필수 수정. 담당 구분은 Phase 1의 합의 대상이다.

### 보강 05. 원본 파일을 열 때 값 자체는 검사하지 않음

**현재 설계.** §6은 원본 파일을 읽을 때 "파일 수·압축 해제 크기·스키마 버전·자산 참조"를 검사한다. §10은 사진을 "디코딩 전후 검사"한다.

**문제.** 필드 값의 범위와 형식을 검사하는 규칙이 없다. 원본 파일은 다른 사람에게 받아서 여는 파일이므로 앱이 만든 값이라고 가정할 수 없다. 사진의 픽셀 크기를 디코딩 전에 어떻게 아는지도 없다.

**영향.**

- 좌표나 크기가 숫자가 아니거나 무한대이면 캔버스가 그리기를 멈추거나 요소가 선택할 수 없는 위치에 놓인다.
- fontFamily에 목록에 없는 문자열이 들어오면 그대로 글꼴 지정 문자열과 textarea 스타일에 쓰인다.
- 파일 크기는 작지만 픽셀 수가 매우 큰 이미지는 디코딩 순간 메모리를 소진해 탭이 종료된다.

**수정안.** 읽기 검증 함수를 하나 두고, 원본 파일을 열 때와 IndexedDB에서 작품을 불러올 때 같은 함수를 통과시킨다. 검사 항목은 다음과 같다.

| 대상 | 검사 |
|---|---|
| 숫자 필드 | 유한한 수인지, 슬라이드 크기 기준의 허용 범위 안인지 |
| 색 | 정해진 표기(예: `#RRGGBB`)인지 |
| fontFamily, align, type | 고정 목록에 있는 값인지 |
| text | 길이 상한 이하인지 |
| 개수 | 슬라이드 수, 장당 요소 수, 획당 점 수가 상한 이하인지 |
| ID | 중복이 없는지, 참조하는 자산이 실제로 있는지 |
| 자산 파일 | 파일 앞부분의 형식 표시가 PNG·JPEG인지. 선언된 mime은 믿지 않는다 |
| 자산 픽셀 크기 | 파일 헤더에서 가로·세로를 읽어 상한을 넘으면 디코딩하지 않는다 |

검사에서 걸린 파일은 열지 않고 현재 작품을 유지한다(§6의 "검증 완료 후 교체"와 같은 경로).

**검증 방법.** 실패 입력 파일을 `tests/fixtures/`에 둔다: 좌표가 문자열인 파일, 목록에 없는 글꼴 이름, 요소 10만 개, 헤더상 픽셀 수가 상한을 넘는 이미지, 확장자와 내용이 다른 자산. 각각 열기가 거부되고 기존 작품이 그대로인지 확인한다.

**최종 판단.** 필수 수정. 상한 값과 허용 목록은 `deserializeProject` 계약의 일부다.

### 보강 06. 사진의 위치 정보 제거와 외부 전송 금지 규칙이 없음

**현재 설계.** §2는 서버 저장 없이 브라우저에서 처리한다. §5의 Asset은 "원본 파일명"을 저장한다. §2는 사진을 PNG·JPEG로 정규화한다.

**문제.**

- 휴대전화로 찍은 사진에는 촬영 위치와 시각이 파일 안에 들어 있다. 정규화가 "큰 사진만 다시 인코딩"으로 구현되면 작은 사진은 원본 그대로 저장되고, 위치 정보가 원본 파일과 PPTX에 실려 다른 사람에게 전달된다.
- 원본 파일명에는 이름이 들어 있을 수 있다(예: `김○○_가족사진.jpg`). 이 값이 `.canvacraft` 파일에 그대로 실린다.
- 앱이 외부 주소로 요청을 보내지 않는다는 규칙이 없다. 글꼴·분석 도구·외부 이미지 주소를 넣는 순간 깨진다.

**영향.** 초등학생이 만든 발표 자료를 친구·교사에게 보내면 집에서 찍은 사진의 촬영 위치가 함께 전달된다.

**수정안.**

1. `importAsset` 계약에 추가한다: 입력 사진은 크기와 관계없이 항상 캔버스로 다시 그려 새 파일로 만든다. 원본 파일의 바이트는 저장하지 않는다.
2. Asset의 원본 파일명은 저장하지 않는다. 화면에 이름이 필요하면 "사진 1"처럼 앱이 붙인다.
3. 제품 규칙으로 적는다: 앱은 자신이 제공된 주소 외에는 어떤 요청도 보내지 않는다. 글꼴·배경·스크립트는 모두 앱과 함께 배포한다. 배포 설정에 콘텐츠 보안 정책(CSP)을 넣어 다른 주소로의 연결을 차단한다.

**검증 방법.**

- 위치 정보가 든 시험 사진을 넣고, 저장된 자산과 PPTX 안의 이미지 파일에 위치 정보가 없는지 확인한다.
- §10의 대표 시나리오를 브라우저 테스트로 수행하는 동안 발생한 모든 네트워크 요청을 기록하고, 앱 주소가 아닌 요청이 0건인지 확인한다.

**최종 판단.** 필수 수정. 어린이가 쓰는 제품에서 가장 먼저 지켜야 할 조건이고, Asset 필드가 바뀐다.

### 보강 07. 그림을 많이 그린 작품이 데이터 형식·성능 기준·취소 한도에 반영되지 않음

**현재 설계.** §10의 대표 문서는 "20장, 장당 요소 50개"다. §5는 획 1개를 요소 1개로 저장하고 취소 기록을 최대 100개로 둔다. StrokeElement는 x, y, width, height와 points를 함께 저장한다.

**문제.**

- 색칠하듯 그리면 한 장에 획이 수백 개 생긴다. 대표 문서는 이 경우를 포함하지 않는다.
- 포인터 입력은 초당 수십~수백 개의 점을 만든다. 점을 줄이는 규칙과 좌표 자릿수 규칙이 없다.
- 획 100개를 그리면 취소 기록이 모두 획으로 채워져 그 전의 사진 이동이나 글씨 수정을 되돌릴 수 없다.
- 획의 width·height는 points에서 계산되는 값인데 따로 저장된다. 두 값이 어긋날 수 있다.

**영향.** 그리기 위주 작품에서 저장 JSON이 수 MB로 커지고 자동 저장·취소·출력이 느려진다. 기본 PPTX가 획별 이미지를 택하면 한 장에 이미지 수백 개가 들어간다.

**수정안.**

1. 획이 확정될 때 점을 줄인다(허용 오차는 논리 0.5px에서 시작해 Phase 2에서 정한다). 좌표는 소수 1자리로 반올림한다. 획당 점 수 상한을 둔다.
2. 획은 위치(x, y)와 points만 저장하고 width·height는 계산한다. 첫 버전에서 획은 이동만 하고 크기 조절은 하지 않는다고 적는다.
3. §10에 대표 문서를 하나 더 둔다: 한 장에 획 300개, 획당 평균 점 200개(초기 목표, Phase 2에서 조정).
4. 취소 한도는 보강 09의 방식으로 메모리 사용을 측정한 뒤 다시 정한다. 한도를 넘으면 가장 오래된 기록부터 버린다는 규칙을 적는다.
5. 기본 PPTX는 연속된 획을 한 이미지로 묶는 방식을 기본으로 한다(§7의 두 안 중 선택).

**검증 방법.** 그림 위주 대표 문서로 자동 저장 시간, 취소 1회 시간, PPTX 생성 시간을 측정한다. 획 100개를 그린 뒤 그 전의 사진 이동을 되돌릴 수 있는지 확인한다.

**최종 판단.** 필수 수정. 점 형식과 저장 필드는 문서 형식이라 Phase 1에서 정해야 한다. 수치는 Phase 2에서 조정한다.

## 4. 해당 Phase 시작 전에 반영할 항목

### 보강 08. 저장 순서와 사진 데이터 정리 시점이 구체적이지 않음

**현재 설계.** §6은 "문서·자산 갱신은 가능한 범위에서 한 트랜잭션"으로, 자산 삭제는 "현재 문서와 실행 취소 기록에서 참조하지 않을 때"로, 여러 탭은 "잠금·충돌 감지를 설계"로 적었다.

**문제와 영향.** IndexedDB 트랜잭션은 대기 중인 요청이 없으면 자동으로 끝난다. 트랜잭션 안에서 사진 해시 계산이나 디코딩을 기다리면 트랜잭션이 닫혀 저장이 실패한다. 문서가 먼저 기록되고 자산 기록 전에 탭이 닫히면, 다시 열었을 때 사진이 빠진 작품이 남는다. 편집 중에 자산을 정리하면 취소 기록이 가리키는 사진을 지울 수 있다.

**수정안.**

1. 자산은 한 번 기록하면 바꾸지 않는다. 내용 해시를 키로 쓴다.
2. 저장 순서를 고정한다: 트랜잭션 밖에서 Blob과 해시를 준비 → 자산 기록 → 문서 기록. 문서 기록이 저장 확정 지점이다. 문서는 이미 기록된 자산만 참조한다.
3. 참조되지 않는 자산의 정리는 작품을 열 때, 편집 잠금을 얻은 직후에만 한다. 편집 중에는 지우지 않는다.
4. 편집 잠금은 Web Locks API(`navigator.locks`)로 구현한다. 잠금을 얻지 못한 탭은 읽기 전용 안내를 띄운다.
5. 시작할 때 `navigator.storage.persist()`를 요청하고 결과와 남은 용량(`navigator.storage.estimate()`)을 저장 상태 화면에 쓴다. 브라우저가 요청을 거절할 수 있으므로 원본 다운로드 안내는 그대로 둔다.
6. 탭이 숨겨질 때(`visibilitychange`) 대기 중인 저장을 즉시 시도한다.
7. Safari는 일정 기간 방문하지 않은 사이트의 브라우저 저장소를 지우는 정책이 있다. iPad를 지원 범위에 넣는다면 Phase 2에서 실제 동작을 확인하고, 마지막 원본 다운로드 이후 경과를 알려 주는 안내를 둔다(Phase 2 확인 필요).

**검증 방법.** 자산 기록과 문서 기록 사이에 탭을 강제 종료하고 다시 열어, 이전 revision이 사진과 함께 온전히 열리는지 확인한다. 두 탭에서 같은 작품을 열어 둘째 탭이 편집하지 못하는지 확인한다.

**최종 판단.** 계획 수정. Phase 8 시작 전에 계약에 넣는다.

### 보강 09. 되돌리기 구현 방식과 다른 장 변경 시 동작이 없음

**현재 설계.** §5는 "명령은 검증된 변경을 한 번에 적용하고 되돌리기 정보를 남긴다"고 적었다. 취소 기록은 작품 전체에 하나다.

**문제와 영향.** 명령마다 "반대 동작"을 따로 만들면 명령 종류 수만큼 되돌리기 오류가 생길 자리가 있다. 또 3번 장을 보는 중에 되돌리기가 1번 장의 변경을 취소하면, 어린이는 아무 일도 일어나지 않았다고 보고 계속 누른다.

**수정안.**

1. 문서를 변경 불가능한 값으로 다루고, 바뀌지 않은 슬라이드·요소는 이전 문서와 같은 객체를 공유한다. 취소 기록은 이전 문서에 대한 참조 목록으로 둔다. 되돌리기는 참조를 바꾸는 일이 되어 명령별 반대 동작이 필요 없다. 사진 바이너리는 문서 밖에 있으므로 복제되지 않는다(§5의 조건 유지).
2. 취소 기록 항목마다 "어느 장에서 일어난 변경인지"를 함께 둔다. 되돌리기·다시 실행은 그 장으로 이동한 뒤 적용한다.
3. 되돌리기 후 선택 상태 규칙을 정한다: 없어진 요소는 선택을 해제한다.

**검증 방법.** 모든 명령에 대해 "실행 → 되돌리기" 뒤 문서가 실행 전과 같은지 한 벌의 공통 테스트로 확인한다. 1번 장을 고치고 3번 장으로 간 뒤 되돌리기를 눌러 1번 장이 화면에 나오는지 확인한다.

**최종 판단.** 계획 수정. Phase 3 시작 전에 정한다.

### 보강 10. 사진을 메모리에 얼마나 올려 둘지 규칙이 없음

**현재 설계.** §10은 사진의 내부 최대 긴 변을 2560px로 한다. §5는 미리보기 캐시를 원본에 저장하지 않는다고만 적었다.

**문제와 영향.** 2560 × 1440 사진 한 장은 디코딩하면 약 14.7MB다(2560 × 1440 × 4바이트). 20장에 사진이 3장씩 있고 모두 디코딩된 채로 유지되면 약 880MB가 된다. 메모리가 적은 PC나 태블릿에서는 탭이 강제 종료된다.

**수정안.**

1. 원본 크기 사진은 현재 장과 내보내기 중인 장에서만 불러온다. 장을 떠나면 해제한다.
2. 왼쪽 미리보기는 작은 비트맵을 캐시해 쓰고, 그 장의 내용이 바뀔 때만 다시 만든다. 미리보기마다 살아 있는 캔버스를 두지 않는다.
3. 화면 표시용으로 더 작은 사본(예: 긴 변 1280px)을 쓸지는 Phase 5에서 메모리를 측정해 정한다. 사본은 저장하지 않는 캐시로 둔다.

**검증 방법.** 20장 × 사진 3장 문서에서 장을 처음부터 끝까지 넘긴 뒤 브라우저 작업 관리자의 탭 메모리를 기록한다. 장 수에 비례해 계속 늘면 실패다.

**최종 판단.** 계획 수정. Phase 3의 렌더러 구조와 Phase 5의 자산 입력 전에 정한다.

### 보강 11. PPTX 변환 규칙 중 줄 간격·여백·배경·손그림 규격이 비어 있음

**현재 설계.** §7은 글씨의 "상자 여백, 줄 간격, 크기, 굵기, 정렬을 명시적으로 변환"하고, 사진 배경을 "슬라이드 뒤쪽 이미지"로, 손그림을 투명 PNG로 내보낸다. §5는 inch = 논리 px / 96을 쓴다.

**문제와 영향, 수정안.** 항목별로 정리한다.

| 항목 | 문제와 영향 | 수정안 |
|---|---|---|
| 좌표 단위 | 소수 inch 계산은 반올림 위치에 따라 1단위씩 어긋난다 | PPTX 내부 단위(EMU)로 1 논리 px = 9525 EMU(914400 ÷ 96)이다. 정수로 떨어지므로 구조 검사에서 값이 정확히 일치하는지 본다 |
| 글씨 크기 | 논리 px × 0.75가 소수 pt가 되면 PowerPoint 글꼴 크기 칸에 어색한 값이 나온다 | 화면에서 고르는 글씨 크기를 4의 배수 px로 둔다(32px → 24pt, 48px → 36pt, 64px → 48pt) |
| 줄 간격 | 화면의 lineHeight는 글씨 크기의 배수다. PowerPoint의 "배수" 줄 간격은 글꼴이 정한 기본 줄 높이의 배수라 같은 1.2라도 결과가 다르다 | 고정 값으로 내보낸다: 줄 간격(pt) = 글씨 크기(px) × lineHeight × 0.75. PptxGenJS의 `lineSpacing`(단위 pt)을 쓴다. 세로 위치 오차는 Phase 2에서 측정한다 |
| 상자 여백 | PptxGenJS 글씨 옵션에 `margin`(pt)과 `inset`(inch)이 모두 있고 둘의 관계가 문서에 없다(공식 문서에서 확인됨) | Phase 2에서 하나를 골라 출력된 슬라이드 XML의 여백 값이 0인지 확인한다. 세로 정렬은 위쪽, 자동 맞춤은 끔으로 고정한다 |
| 사진 배경 | PptxGenJS 이미지의 `cover` 방식은 "영역이 이미지보다 크면 줄어들지 않고 늘어난다"는 주의가 문서에 있다(공식 문서에서 확인됨). 화면의 가운데 채우기와 결과가 다를 수 있다 | 내보낼 때 화면과 같은 규칙으로 16:9로 미리 자른 이미지를 만들어 넣는다. 슬라이드 배경(`slide.background`)으로 넣을지 뒤쪽 이미지로 넣을지는 Phase 2에서 PowerPoint로 비교한다. 배경으로 넣으면 실수로 끌려 움직이지 않는다 |
| 손그림 PNG | 배율과 여백이 없다. 점 좌표만으로 영역을 잡으면 선 굵기의 절반과 둥근 끝이 잘린다 | 배율은 논리 크기의 2배(PDF 목표 해상도와 같음). 영역은 점 범위에 선 굵기 절반 + 2px를 더한다 |
| 손그림을 도형으로 | PptxGenJS는 v3.7.0부터 자유형 도형을 지원하지만 도형 선의 끝 모양(둥글게) 옵션은 문서에 없다(공식 문서에서 확인됨) | 첫 버전은 PNG를 유지한다. 이 이유를 설계에 적어 둔다. 편집 가능한 획이 필요해지면 Phase 2 시험 대상에 추가한다 |

**검증 방법.** 생성된 PPTX의 압축을 풀어 슬라이드 XML에서 요소 순서, 위치·크기(EMU), 글씨 내용, 글씨 크기, 줄 간격, 여백을 읽어 기대값과 비교하는 자동 테스트를 둔다. 화면 모양(세로 위치, 배경 잘림, 획 가장자리)은 실제 PowerPoint에서 화면 캡처와 겹쳐 비교한다.

**최종 판단.** 계획 수정. Phase 2 시험 항목에 넣고, 결과를 Phase 9 계약에 반영한다.

### 보강 12. PDF 페이지 이미지의 형식과 용량 기준이 없음

**현재 설계.** §7은 각 슬라이드를 2560 × 1440 이미지로 만들어 PDF 페이지에 넣는다. §10의 출력 목표는 20장 30초다.

**문제와 영향.** 이미지 형식이 정해져 있지 않다. 사진이 들어간 장을 PNG로 넣으면 장당 수 MB 이상이 될 수 있어 20장 파일이 메일·메신저로 보내기 어려운 크기가 된다. 형식에 따라 PDF 생성 시간도 달라진다.

**수정안.** Phase 2에서 같은 20장 문서를 PNG와 JPEG(품질 0.85~0.9)로 각각 만들어 파일 크기, 생성 시간, 글씨 가장자리 품질을 기록하고 형식을 정한다. 슬라이드는 투명한 부분이 없으므로 JPEG를 쓸 수 있다. 파일 크기 상한(예: 20장 30MB)을 §10에 목표로 추가한다.

**검증 방법.** 사진 위주 20장 문서와 글씨 위주 20장 문서로 각각 측정한다. 크기 상한과 30초 목표를 둘 다 만족하는 형식을 고른다.

**최종 판단.** 계획 수정. Phase 2 시험 항목에 추가한다.

### 보강 13. 편집기 입력 처리에 빠진 세부 규칙

**현재 설계.** §3과 Phase 4·6·7이 조작 규칙을 적었다. 아래 항목은 빠져 있다.

| 규칙 | 빠졌을 때 생기는 일 | 넣을 곳 |
|---|---|---|
| Konva의 크기 조절 도구는 width·height가 아니라 확대 비율(scaleX·scaleY)을 바꾼다. 조절이 끝나면 비율을 width·height(글씨는 글씨 크기)로 환산해 명령으로 보내고 비율은 1로 되돌린다 | 비율이 누적되어 저장된 크기와 화면 크기가 달라지고 선 굵기까지 확대된다 | Phase 4 계약 |
| 한글 조합 중의 키 입력은 `isComposing`이 참이거나 keyCode가 229다. 이 경우 Enter·Escape·Delete 단축키를 처리하지 않는다 | 조합 중 Enter가 입력 확정으로 처리되어 마지막 글자가 중복되거나 사라진다 | Phase 6 계약 |
| textarea의 표시 배율은 글씨 크기를 줄이지 않고 CSS `transform: scale`로 맞춘다. 줄 간격은 px로 지정한다 | 작은 배율에서 브라우저의 최소 글씨 크기에 걸려 입력 위치가 어긋난다. iOS에서는 16px 미만 입력란에 초점이 가면 화면이 자동 확대된다(Phase 2 확인 필요) | Phase 6 계약 |
| 편집을 끝냈을 때 내용이 비어 있으면 글씨 상자를 삭제하고 취소 기록을 남기지 않는다 | 보이지 않는 빈 상자가 쌓이고 PPTX에 빈 텍스트 상자가 나온다 | Phase 6 계약 |
| 그리기 중에는 처음 닿은 포인터 하나만 따라간다. 캔버스에 `touch-action: none`을 주고 포인터를 캡처한다 | 손바닥이 닿으면 획이 튀고, 그리는 중에 화면이 스크롤되거나 확대된다 | Phase 7 계약 |
| 다운로드 파일 이름은 작품 이름에서 Windows에서 파일 이름에 쓸 수 없는 문자(역슬래시, 슬래시, 콜론, 별표, 물음표, 큰따옴표, 꺾쇠괄호, 세로선)를 바꾸고, 비어 있으면 기본 이름을 쓴다 | 제목에 `?`나 `:`가 있으면 다운로드가 실패하거나 이름이 잘린다 | Phase 8·9 계약 |

**검증 방법.** 각 규칙에 실패 입력을 하나씩 둔다: 크기 조절을 5회 반복한 뒤 저장값과 화면 크기 비교, 조합 중 Enter, 표시 배율 50%에서 입력 위치, 빈 상자 확정, 두 손가락 동시 입력, 제목 `우리 가족: 소개?`로 다운로드.

**최종 판단.** 계획 수정. 각 Phase의 작업 요청에 포함한다.

### 보강 14. 편집·저장·출력이 Phase 9에서 처음 정식으로 만남

**현재 설계.** Phase 2에서 작은 시험 코드로 출력을 확인하고, 정식 출력 변환기는 Phase 9에서 만든다. §9는 그 사이 Codex가 어댑터를 준비할 수 있다고 적었다.

**문제와 영향.** Phase 5~7에서 요소 형식이 바뀌면 출력 쪽 가정이 깨져도 Phase 9까지 드러나지 않는다. 일정의 뒤쪽에서 데이터 구조를 고치게 된다.

**수정안.**

1. Phase 3 완료 기준에 추가한다: 모든 요소 종류가 든 공통 샘플 문서가 "화면 표시 → 저장 → 다시 열기 → PPTX·PDF 출력"까지 한 번에 통과한다. 출력 품질은 낮아도 된다.
2. Phase 4~8의 각 완료 기준에 "공통 샘플 문서의 전체 흐름이 여전히 통과함"을 넣는다. 새 필드가 생기면 샘플 문서에 먼저 추가한다.
3. PPTX는 보강 11의 구조 검사를 자동 테스트로 돌린다. 실제 PowerPoint 확인은 §10대로 사람이 한다.
4. 한글 조합은 Chromium의 개발자 도구 프로토콜로 조합 이벤트를 만들어 회귀 테스트를 보탠다. 실제 입력기 확인을 대신하지는 않는다(§10의 원칙 유지).

**검증 방법.** 각 Phase 인계 기록에 공통 샘플 문서의 전체 흐름 실행 결과를 붙인다.

**최종 판단.** 계획 수정. Phase 3 시작 전에 완료 기준에 넣는다.

### 보강 15. 라이브러리 버전과 참고 문서의 시점이 맞지 않음

**현재 설계.** §4는 라이브러리를 후보로 두고 Phase 2에서 버전을 고정한다.

**확인한 내용(공식 문서에서 확인됨, 2026-11-06).**

| 라이브러리 | 확인한 내용 |
|---|---|
| PptxGenJS | 릴리스 페이지의 최신은 v4.0.1이다. 문서 사이트의 페이지별 갱신일은 2022~2025년이다. 자유형 도형은 v3.7.0 릴리스 노트에만 있고 문서 사이트에는 설명이 없다 |
| pdf-lib | 릴리스 페이지의 최신은 v1.17.1이다 |
| Konva | 릴리스 페이지의 최신은 10.9.1이다 |
| react-konva | README에 따르면 React Konva 19.3은 React 19.3, 19.2는 React 19.2, 18은 React 18과 짝이다 |

**문제와 영향.** PptxGenJS는 문서 사이트가 설치 버전보다 오래됐을 수 있다. 문서만 보고 계약을 쓰면 옵션 이름이나 동작이 다를 수 있다. react-konva는 React 버전과 짝이 맞지 않으면 설치 단계에서 충돌한다.

**수정안.**

1. Phase 2에서 설치한 패키지의 타입 정의 파일을 기준으로 옵션을 확인한다. 문서 사이트는 참고로만 쓴다.
2. React와 react-konva의 버전 짝을 계약 문서에 숫자로 적는다.
3. pdf-lib는 Phase 2에서 마지막 릴리스 날짜와 미해결 이슈를 확인해 유지보수 상태를 기록한다. 문제가 있으면 대체 후보를 함께 적는다.
4. 같은 사진을 여러 장에 썼을 때 PptxGenJS가 이미지 파일을 한 번만 넣는지 Phase 2에서 출력 파일을 풀어 확인한다(Phase 2 확인 필요).

**최종 판단.** 계획 수정. Phase 2 산출물 "의존성 버전 결정"에 포함한다.

### 보강 16. 작품을 몇 개 보관하는지, 공용 PC에서 어떻게 지우는지 미정

**현재 설계.** §3에 "작품 이름"과 "기존 작품 교체"가 있다. 작품 목록 화면은 없다. 자동 저장은 브라우저에 남는다.

**문제와 영향.** 작품이 한 개인지 여러 개인지에 따라 IndexedDB 구조, 자산 정리 범위, 탭 잠금 단위가 달라진다. 학교 컴퓨터실처럼 여러 명이 쓰는 PC에서는 다음 사용자가 앱을 열면 앞 사용자의 작품과 가족 사진이 그대로 나온다. 반대로 재시작할 때 초기화되는 PC나 시크릿 창에서는 자동 저장이 사라진다.

**결정할 것.**

| 질문 | 권장 |
|---|---|
| 작품을 여러 개 보관하는가 | 여러 개. 시작 화면에 작품 목록과 미리보기를 둔다. 초등학생은 과제마다 새 작품을 만든다 |
| 공용 PC에서 지우는 방법 | 작품마다 "이 컴퓨터에서 지우기"를 두고, 지우기 전에 원본 다운로드를 권한다 |
| 저장이 유지되지 않는 환경 | 시작할 때 브라우저 저장소를 쓸 수 있는지 확인하고, 안 되면 "끝낼 때 꼭 원본을 내려받으세요" 안내를 띄운다 |

**결정(2026-11-06).** 작품을 여러 개 보관한다. 시작 화면에 작품 목록과 미리보기를 두고, 작품마다 "이 컴퓨터에서 지우기"를 제공한다.

이 결정에 따라 Phase 1 계약에 다음을 넣는다.

- IndexedDB의 문서 기록은 작품 ID를 키로 한다. 작품 목록 화면이 쓰는 요약 정보(이름, 수정 시각, 첫 장 미리보기)를 문서 본문과 따로 둔다. 목록을 띄우려고 모든 작품의 본문을 읽지 않게 하기 위해서다.
- 자산은 내용 해시를 키로 하므로 여러 작품이 같은 사진을 공유할 수 있다. 작품을 지울 때는 다른 작품이 참조하지 않는 자산만 지운다(보강 08의 정리 규칙을 "모든 작품 기준"으로 넓힌다).
- 편집 잠금은 작품 단위로 건다. 서로 다른 작품은 두 탭에서 동시에 편집할 수 있다.
- §3의 "기존 작품 교체" 확인은 원본 파일을 열 때 필요 없어진다. 열린 파일은 새 작품으로 목록에 추가한다.

**검증 방법.** 사진 한 장을 두 작품에 넣고 한 작품을 지운 뒤, 남은 작품의 사진이 그대로인지 확인한다. 작품을 지운 뒤 브라우저 저장소에 그 작품의 문서·미리보기·전용 자산이 남아 있지 않은지 확인한다.

**최종 판단.** 필수 수정. Project 저장 구조와 자산 정리 범위가 바뀌므로 Phase 1 계약에 반영한다.

### 보강 17. PPTX를 여는 프로그램이 PowerPoint만 가정됨

**현재 설계.** Phase 2와 9는 "실제 PowerPoint"에서 확인한다.

**문제와 영향.** 국내 학교에서는 한컴오피스 한쇼, Google Slides, PowerPoint 웹 버전으로 PPTX를 여는 경우가 있다. 이 프로그램들은 글꼴 대체와 줄바꿈이 PowerPoint 데스크톱과 다를 수 있고, 지금 계획에서는 그 차이를 볼 기회가 없다.

**결정할 것.** 어느 프로그램까지 "공식 지원"이고 어느 것이 "참고 확인"인지 정한다. 권장: PowerPoint 데스크톱(Windows)을 공식 지원으로 두고, 한쇼·Google Slides·PowerPoint 웹은 Phase 2에서 한 번 열어 차이를 기록만 한다. 차이가 크면 다운로드 화면에서 "모양 그대로 PPT"를 안내한다.

**결정(2026-11-06).** Windows의 PowerPoint 데스크톱만 공식 지원한다. 한쇼, Google Slides, PowerPoint 웹은 Phase 2에서 같은 예제 파일을 한 번 열어 차이를 기록만 한다. 이 세 프로그램에서의 모양 차이는 Phase 9 완료 기준에 넣지 않는다.

**검증 방법.** Phase 2 산출물에 프로그램별 화면 캡처와 차이 목록을 남긴다. 차이가 줄 수 변화나 요소 겹침 수준이면 다운로드 화면에 "PowerPoint가 아닌 프로그램에서는 '모양 그대로 PPT'를 권합니다" 안내를 넣는다.

**최종 판단.** 계획 수정. Phase 2 시험 항목과 사용 설명의 알려진 제약에 반영한다.

### 보강 18. 기준 기기와 조작 반응 기준이 한 줄로만 있음

**현재 설계.** §10은 "선택·이동 반응 100ms 이내"를 목표로 하고 기준 기기는 Phase 2에서 기록한다.

**문제와 영향.** 끌어서 옮기는 동안 화면이 100ms마다 한 번 갱신되면 초당 10번이라 끊겨 보이는데도 기준을 통과한다. 기준 기기가 개발용 PC이면 학교 PC에서의 체감과 다르다.

**결정할 것.**

- 반응 기준을 둘로 나눈다. 권장: 눌러서 선택되기까지 100ms 이내, 끌기·그리기 중 화면 갱신 간격 33ms 이내(초당 30회 이상).
- 기준 기기를 "지원할 가장 낮은 사양"으로 정한다. 사용자가 실제로 쓸 PC·태블릿의 사양을 알려 주면 Phase 1에 적는다.

**결정(2026-11-06).** 기준 기기는 RAM 8GB의 일반 PC(최근 5년 안의 보급형 노트북 수준)로 한다. Phase 2에서 실제로 측정에 쓴 PC의 CPU·메모리·OS·브라우저 버전을 기록한다.

이 결정의 범위는 다음과 같다.

- §10의 성능 목표(조작 반응, 그리기, 출력 30초)는 이 기기에서 측정한다. RAM 4GB급 PC와 태블릿에서는 성능 목표를 보장하지 않고, 알려진 제약으로 적는다.
- 태블릿의 터치 조작은 §2대로 기능 동작만 확인한다.
- 보강 10의 사진 메모리 규칙은 그대로 적용한다. 사진이 많은 작품의 메모리 사용량은 기준 기기에서도 문제가 되는 크기다.
- 반응 기준을 둘로 나누는 안(선택 100ms, 끌기·그리기 중 화면 갱신 33ms)은 검토자의 권장이다. Phase 2에서 기준 기기로 측정한 뒤 확정한다.

**최종 판단.** 계획 수정. Phase 2 시작 전에 §10에 반영한다.

### 보강 19. 요소 복제, 이모지, iPad 사진 형식의 범위가 정해지지 않음

| 질문 | 왜 지금 정해야 하는가 | 권장 |
|---|---|---|
| 요소 복제(같은 그림·글씨를 하나 더)를 첫 버전에 넣는가 | §2에 슬라이드 복사는 있고 요소 복제는 없다. Ctrl+V는 이미 사진 붙여넣기에 쓰이므로 요소 붙여넣기와 구분 규칙이 필요하다 | "복제" 버튼만 넣는다. Ctrl+C·V로 요소를 복사하는 기능은 후속 범위로 둔다 |
| 이모지를 글씨에 쓸 수 있는가 | 어린이는 이모지를 넣는다. 이모지는 기기마다 그림이 다르고 줄 나누기에서 한 글자가 둘로 쪼개질 수 있다 | Phase 2 시험 문장에 이모지를 넣어 화면·PPTX·PDF 결과를 본 뒤 "지원" 또는 "입력은 되지만 모양은 기기마다 다름"으로 정한다 |
| iPad 사진 보관함의 HEIC 사진 | §2의 입력 형식은 PNG·JPEG·WebP다. iPad가 파일 선택 때 JPEG로 바꿔 주는지는 확인되지 않았다 | §2에서 iPad 지원 범위를 정하는 Phase 2 시험에 "사진 보관함에서 고르기"를 추가한다 |

**결정(2026-11-06).** 요소 복제는 "복제" 버튼만 첫 버전에 넣는다. Ctrl+C·V로 요소를 복사하는 기능은 후속 범위다. Ctrl+V는 사진 붙여넣기에만 쓴다.

이 결정에 따라 Phase 1 명령 목록에 요소 복제 명령을 추가한다. 규칙은 다음과 같다: 복제본은 새 ID를 받고, 원본에서 조금 떨어진 위치(예: 오른쪽 아래로 논리 20px)에 놓이며, 슬라이드 범위를 벗어나면 안쪽으로 당긴다. 사진 요소의 복제본은 같은 자산을 공유한다(§5의 슬라이드 복사 규칙과 같음). 복제 1회는 취소 1회다.

**최종 판단.** 요소 복제는 필수 수정(Phase 1 계약에 반영). 이모지와 iPad 사진 형식은 확인 후 결정으로 남기고 Phase 2 측정으로 정한다.
