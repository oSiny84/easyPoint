# Phase 2 기술 시험 결과

갱신: 2026-11-06. 개발 PC에서 실행해 확인한 결과와 아직 확인하지 못한 항목을 구분해 적는다. 전체 진행 상태는 [PROGRESS.md](PROGRESS.md)를 본다.

## 1. 요약

자동으로 비교할 수 있는 항목 10개를 실행해 결정 11건을 내렸다(줄 위치 항목에서 줄 나누기와 공백 폭 2건이 나왔다). 물리 기기나 사람의 조작이 필요한 항목 8개는 미검증이다. Phase 2 전체 완료가 아니다.

| 항목 | 결정 | 근거 수치 |
|---|---|---|
| 글씨 줄 나누기 | 브라우저 DOM에서 측정하고 `word-break: keep-all`을 쓴다 | 실제 textarea와 40개 중 40개 일치. PowerPoint 자동 줄바꿈과도 40개 중 40개 일치(Noto Sans KR 설치 상태) |

사용자가 뒤집을 수 있는 결정은 PPT 글꼴이다. 받는 PC와 관계없이 같은 모양이 나오는 대신, 앱 화면과 글꼴이 달라 줄이 13/40 사례에서 다르게 나뉜다.

## 2. 측정 환경과 한계

- PC: AMD Ryzen 7 8700G, RAM 약 31GB, Windows 11. PowerPoint 16.0(COM 자동화). Chromium은 Playwright headless shell.
- **이 PC에는 Noto Sans KR이 설치되어 있다**(`C:\Windows\Fonts\NotoSansKR-VF.ttf`). 그래서 이전 PowerPoint 렌더 결과는 글꼴이 없는 PC의 모습이 아니었다. 시스템 글꼴을 지우지 않고 없는 글꼴 이름(`CanvaCraft Missing Font`)을 지정해 대체 동작을 대신 관찰했다. 실제 Noto Sans KR이 없는 PC의 결과와 다를 수 있다.
- CPU 4배 제한은 느린 PC의 대용이다. RAM 8GB 기기 측정이 아니다.
- 사진은 세부가 많은 합성 그림이다(평균 668KB JPEG). 실제 사진 문서는 측정하지 않았다.
- 줄 간격 1.3, 왼쪽 정렬만 시험했다. 다른 줄 간격의 세로 보정값과 가운데·오른쪽 정렬의 줄 끝 공백은 Phase 6에서 측정한다.
- PDF 확인은 PyMuPDF 렌더다. Edge·Acrobat에서 열어 보지 않았다.
- COM으로 연 파일은 복구 안내 창이 뜨는지 알 수 없다. 더블클릭 열기는 미검증이다.

## 3. 글씨 줄 나누기

**시험 방법.** 문장 8종(띄어쓰기 없는 한글, 어절, 한영 혼합, 문장부호, 이모지, 개행, 연속 공백, 긴 영문)과 폭·글씨 크기 5종을 곱한 40개 사례를 썼다. 실제 앱에서 편집 전·편집 중·편집 후 화면과 출력 렌더를 캡처해 글자 잉크의 줄 띠를 비교했다. 시험 코드는 `tests/phase2/lines.spec.ts`다.

| 비교 | 수정 전 | 수정 후 |
|---|---|---|
| layoutText와 실제 textarea의 줄 | 24/40 일치. `English`가 `En`/`glish`로 잘림 | 40/40 일치 |
| 줄 띠 수(화면·편집·편집 후·출력) | 4/40 불일치 | 0/40 불일치(배율 0.84, 0.49 모두) |
| 편집 전후 세로 차이 | - | 최대 1.19 논리px(배율 0.84), 4.05 논리px(배율 0.49, 화면 2px) |
| 화면과 출력의 세로 차이 | 최대 14.5 논리px, 약 0.23em 위로 | 최대 1.22 논리px |

**공백 폭 원인(실행으로 확인).** Noto Sans KR은 `lang=ko`에서 공백이 0.28em이고 그 외에는 0.224em이다. DOM은 `lang`을 따르지만 캔버스는 한글이 섞인 문장에서 0.224em을 썼다. 글꼴 파일을 나눈 것과는 관계없었다. 그래서 줄 수는 같아도 편집을 시작하면 공백이 있는 문장의 글자가 옆으로 움직였다. 언어 미지정(`und`)으로 맞춰 해결했다. 편집 영역의 언어 표시가 사라지므로 스크린 리더 영향은 Phase 10 사용성 점검에서 확인한다.

**줄 계산 시간.** 50자 0.3ms, 500자 4ms, 5,000자(상한) 39ms다. 지금은 렌더마다 다시 계산하므로 Phase 6에서 같은 입력의 결과를 캐시한다.

## 4. PowerPoint 비교

**시험 방법.** 같은 40개 사례를 PPTX로 만들어 `scripts/phase2-powerpoint.ps1`로 열었다. COM `TextRange.Lines()`로 PowerPoint가 실제 나눈 줄을 읽고, PNG로 내보내 앱 렌더와 비교했다. PDF로 저장해 실제 사용된 글꼴도 확인했다.

| 후보 | 줄 내용 일치 | 줄 수 일치 | 상자 오른쪽 넘침 | 오른쪽 끝 평균 차이(논리px) | 실제 사용 글꼴 |
|---|---|---|---|---|---|
| Noto 지정, 자동(이 PC에 설치됨) | 40/40 | 40/40 | 0 | 1.89 | Noto Sans KR 모양(PDF 글꼴 이름은 Calibri로 나옴) |
| 없는 글꼴 지정, 자동, lang=ko-KR | 19/40 | 32/40 | 2 | 24.71 | 맑은 고딕 + YaHei + Calibri |
| 없는 글꼴 지정, 자동, lang=en-US | 8/40 | 35/40 | 0 | 22.05 | 맑은 고딕 + Calibri |
| 없는 글꼴 지정, 줄 고정 | 40/40 | 40/40 | 18 | 20.62 | 맑은 고딕 + YaHei + Calibri |
| 맑은 고딕, 자동 | 11/40 | 31/40 | 2 | 30.31 | 맑은 고딕 |
| **맑은 고딕, 자동, 0.92배(선택)** | 27/40 | 35/40 | 0 | 1.27 | 맑은 고딕 |
| 맑은 고딕, 줄 고정 | 40/40 | 40/40 | 21 | 27.76 | 맑은 고딕 |

- 한글 폭은 맑은 고딕이 Noto Sans KR보다 약 9% 넓다. 0.92배로 맞추면 한글 위주 문장이 일치하고, 남은 차이는 영문·연속 공백이 많은 문장에서 생긴다.
- 상자 폭을 3% 늘린 후보는 줄 수 일치가 그대로 35/40이고 넘침만 9건 늘어 버렸다.
- 줄 간격 배수(`lineSpacingMultiple`)는 줄이 내려갈수록 어긋나(최대 55.5 논리px) 버렸다. 고정 줄 간격만 쓴다.
- 위 두 제외 후보(상자 폭, 줄 간격 배수)는 탈락 후 시험 코드에서 뺐으므로 재실행 결과 파일에는 나오지 않는다.
- PptxGenJS `softBreakBefore`는 줄 간격과 함께 쓰면 `<a:br/>` 뒤에 `<a:pPr>`를 넣어 스키마를 어긴다. 쓰지 않는다.
- 줄 간격별 보정(Phase 6, `tests/phase2/lineheight.spec.ts`): 고정 줄 간격에서 줄 간격 1~2, 글씨 크기 24·36·64px를 재서 상자 y 보정을 fontSize×(0.07−0.25×(lineHeight−1.3))로 정했다. 보정 전 첫 줄 차이는 최대 11 논리px, 보정 후 두 줄 모두 1.5 논리px 이내다.
- 실제 저장 시험: PowerPoint에서 글씨를 수정하고 사진을 옮겨 저장한 뒤 다시 열어 값이 유지됨을 확인했다. COM 조작이며 사람의 손 조작은 아니다.

## 5. 배경과 이미지 저장

| 방식 | 앱 렌더와 평균 차이(4가지 비율) | 판단 |
|---|---|---|
| 미리 자른 JPEG를 슬라이드 배경으로 | 1.17~1.45 | 선택. 어린이가 PowerPoint에서 실수로 끌 수 없다 |
| 미리 자른 JPEG를 맨 뒤 이미지로 | 1.17~1.45 | 같은 모양. 끌려 움직일 수 있어 제외 |
| 원본을 PptxGenJS `sizing: cover`로 | 2.07~12.11 | 제외. 16:9가 아닌 사진에서 잘리는 위치가 틀리다 |

PptxGenJS는 같은 사진을 장마다 따로 저장하고 JPEG 배경에 `.png` 이름을 붙인다. `finishPptx`가 내용 해시로 합치고 실제 형식의 확장자를 붙인다. 합친 파일 20장 모두 PowerPoint에서 열려 렌더됐고 관계 파일의 대상 누락은 0건이다. 슬라이드 복사를 자주 하는 어린이 작품에서 파일 크기를 크게 줄인다.

## 6. 성능(개발 PC)

**시험 문서.** 그림 문서는 한 장에 300획×200점이다. 사진 문서는 20장×서로 다른 합성 사진 3장(합계 39.1MB)이다. 시험 코드는 `tests/phase2/perf.spec.ts`다.

| 조작(300획 문서) | 재구성 전 처리 시간 p95 | 재구성 후 p95 | CPU 4배 제한 재구성 후 p95 |
|---|---|---|---|
| 그리기 입력 1회 | 109ms | 1.6ms | 6.8ms |
| 글씨 끌기 입력 1회 | 56.7ms | 1.5ms | 6.4ms |
| 끌기 시작 1회(최대값) | - | 105ms | 460ms |

재구성은 두 가지다. 그리는 중인 획은 별도 레이어에 직접 그리고, 끌리는 요소는 끄는 동안 별도 레이어로 옮긴다. 값은 입력 후 메인 스레드 처리까지의 시간이며 화면 표시 지연 전체가 아니다. 프레임 간격은 끌기·그리기 모두 p95 16.8ms였다.

끌기 시작 때 기존 요소를 한 번 다시 그리므로 선택 반응 목표 100ms를 극단적인 그림 문서에서 넘는다. 이 시험 문서는 화면이 획으로 가득 찬 수준이다. Phase 7에서 레이어 캐시로 개선할지 정한다.

| 출력(20장×사진 3장) | 크기 | 시간 |
|---|---|---|
| PDF PNG | 75.8MB | 12.0초 |
| PDF JPEG 0.85 / 0.88 / 0.90 | 8.0 / 9.1 / 10.0MB | 약 2.2초 |
| 편집용 PPT | 39.2MB | 3.7초 |
| 모양 그대로 PPT (JPEG 0.88) | 8.8MB | 3.2초 |

JPEG 0.88의 글씨 영역 PSNR은 41.7dB이며, 렌더한 PDF에서 글씨 가장자리를 눈으로 확인해 문제를 찾지 못했다. 20장 사진 PPTX는 PowerPoint에서 20장 모두 열렸다.

메모리는 브라우저 전체 프로세스 합계 기준이다. 시작 397MB, 20장 차례 표시 후 약 1.04GB(5장 이후 15MB 안팎씩만 증가), 출력 후 최대 약 1.44GB다. 장 전환은 약 100ms다. RAM 8GB 기기에서 이 값이 유지되는지는 확인하지 못했다.

## 7. 미검증 항목

| 항목 | 필요한 것 | 영향 |
|---|---|---|
| 실제 Windows 한글 입력기 | 사람이 키보드로 입력 | 현재는 CDP 조합 입력만 확인. `lang="und"` 변경 후 입력기 동작도 포함 |
| PPT·PDF 더블클릭 열기 | 사람이 파일을 열어 복구 안내 창 여부 확인 | `finishPptx`가 파일 내부를 고치므로 꼭 필요 |
| 글꼴 없는 실제 PC | Noto Sans KR이 없는 Windows PC | 맑은 고딕을 쓰므로 영향은 작다 |
| 물리 터치 기기 | 터치 PC 또는 태블릿 | CDP 터치 취소만 확인 |
| iPad 사진 보관함·HEIC | iPad | 확인 전까지 iPad는 공식 지원에서 제외, HEIC는 미지원 안내 |
| 한쇼·PowerPoint 웹·Google Slides | 프로그램 또는 외부 업로드 | 공식 지원 대상이 아니라 차이 기록만 남은 상태. 외부 서비스 업로드는 사용자 판단 |
| RAM 8GB 기준 기기 | 해당 PC | 성능 목표 확정에 필요 |
| 실제 사진 문서 | 사용자가 고른 사진 | 합성 사진 수치의 현실성 확인 |

## 8. 재실행 방법

```bash
npm run test:phase2 -- lines pptx-make background perf
```

```bash
pwsh -NoProfile -File scripts/phase2-powerpoint.ps1
```

```bash
pwsh -NoProfile -File scripts/phase2-powerpoint.ps1 -Dir artifacts/phase2/bg
```

```bash
npm run test:phase2 -- pptx-compare background
```

시험 화면은 `/probe.html`(`src/probe`)로 옮겨 고정했고 제품 코드는 Phase 3에서 `src/rendering`, `src/export`로 옮겼다. 결과는 `artifacts/phase2/`에 생긴다(Git 제외). 주요 파일은 `lines-*.json`, `pptx-compare.json`, `background-compare.json`, `perf.json`이다. PowerPoint 스크립트는 사용자가 이미 열어 둔 PowerPoint를 닫지 않는다.
