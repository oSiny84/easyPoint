## 1. 목표와 전체 계획

어린이가 사진, 배경, 손그림, 글씨로 여러 장의 슬라이드를 만들고, 작업을 이어서 편집하거나 PPTX·PDF로 내려받는 웹앱을 만든다. PPTX에서는 글씨와 사진을 개별 수정할 수 있게 하고, 손그림은 이미지로 보존한다.

| 단계 | 결과 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1 | 요구사항·화면 흐름·데이터 계약 확정 | 기능 범위와 상태 소유자가 문서에 정리됨 |
| 2 | 한글·그리기·출력의 기술 검증 | 실제 브라우저와 PowerPoint에서 핵심 사례를 관찰함 |
| 3 | 앱 구조·문서 상태·명령 체계 | 같은 문서 상태로 화면 표시와 편집 명령이 연결됨 |
| 4 | 슬라이드 관리·선택·이동·크기 조절 | 좌표 변환, 순서 변경, 취소·다시 실행이 일관됨 |
| 5 | 사진·배경 입력 | 사진·배경이 저장 가능한 원본 데이터로 남음 |

| 7 | 자유 그리기·지우기 | 마우스·터치 그림과 다른 요소의 순서가 보존됨 |

| 10 | 통합 검증·어린이 사용성·출시 준비 | 필수 시나리오 통과, 알려진 제약과 배포 절차 기록 |

## 2. 제품 범위와 기본 가정

대상은 초등학생이며, 1차 지원 환경은 Windows의 Chrome·Edge와 마우스·키보드다. 태블릿 가로 화면의 터치 조작을 설계에 포함한다. iPad Safari는 2단계에서 입력·다운로드를 시험한 뒤 공식 지원 범위를 정한다. 휴대전화 편집은 후속 범위다.

첫 버전은 로그인과 서버 저장 없이 브라우저에서 편집·저장·내보내기를 처리한다. 브라우저 저장은 영구 보관을 보장하지 않으므로 별도 원본 파일 다운로드를 제공한다. 서비스 최초 접속 후의 완전한 오프라인 사용은 첫 버전의 보장 범위에 넣지 않는다.

### 포함 기능

- 16:9 슬라이드. 새 장, 복사, 삭제, 순서 변경. 마지막 한 장은 삭제 대신 내용 비우기로 안내한다.
- 파일 선택·끌어놓기·클립보드 이미지 붙여넣기. PNG·JPEG·WebP를 입력 대상으로 하고 내부에서는 출력에 적합한 PNG·JPEG로 정규화한다.
- 사진 이동·비율 유지 크기 조절·삭제·앞뒤 순서 변경. 초기 버전의 사진은 전체 이미지가 보이게 하며 자유 자르기·회전은 후속 기능으로 둔다.
- 단색 배경, 제공 배경, 사용자 사진 배경. 배경 사진은 가운데 기준 채우기로 표시하고 이 규칙을 출력에도 적용한다.
- 일반 텍스트 상자. 한글·영문·숫자, 여러 줄, 글꼴 선택, 크기, 색, 굵게, 왼쪽·가운데·오른쪽 정렬. 한 상자 안의 부분별 서식은 제외한다.
- 자유 그리기. 펜 색·굵기, 획 단위 지우기, 획 선택·이동. 부분을 문질러 지우는 픽셀 지우개는 후속 기능이다.
- 실행 취소·다시 실행, 자동 저장 상태, 원본 다운로드·열기, 전체 화면 발표, PPTX·PDF 출력.

### 후속 범위

회원·교실·과제 제출, 클라우드 동기화, 공동 편집, AI 생성, 영상·음성, 애니메이션, PPTX 가져오기, 외부 이미지 검색, 복잡한 도형·그룹·표는 첫 버전에서 제외한다. Canva의 템플릿·그림을 가져오는 방식이 아니라 직접 제작하거나 사용 권한을 확보한 자산을 사용한다.

## 3. 어린이용 화면과 입력 규칙

UI_REFERENCE.md를 확정 기준으로 사용한다. 기존의 왼쪽 세로 슬라이드 목록·상단 도구 중심 배치 제안은 폐기한다. 상단 바, 왼쪽 세로 도구와 펼쳐지는 패널, 중앙 슬라이드, 아래 가로 장 목록, 오른쪽 아래 확대/축소를 유지한다.

도구는 디자인 / 요소 / 텍스트 / 업로드 / 그리기 / 배경이다. 요소에는 도형·캐릭터·스티커를 넣고 차트는 제외한다. 상세 패널·선택·입력·단축키·다운로드 경로와 구현 완료 기준은 UI_REFERENCE.md §2~6을 따른다.

## 4. 기술 구성 제안

| 부분 | 후보 | 선택 이유 및 확인 조건 |
|---|---|---|
| 앱 | React + TypeScript + Vite | 화면과 문서 타입을 분리하고 정적 웹앱으로 배포 |
| 편집 화면 | Konva + react-konva | 사진·텍스트·선과 선택 조작 구현. React와 호환되는 버전 조합 고정 |
| 글씨 입력 | 캔버스 위 HTML textarea | 실제 입력은 DOM에서 처리해 한글 조합과 커서 지원 |
| 상태 | 단일 문서 저장소와 명령 처리기 | 화면과 출력에서 서로 다른 원본 상태를 갖지 않도록 함 |
| 자동 저장 | IndexedDB | 문서와 이미지 Blob 저장. 저장 실패·용량 초과 처리 필요 |
| 원본 파일 | ZIP + JSON + assets | 다른 기기로 파일을 옮겨 재편집. ZIP 도구는 2단계에서 선택 |
| PPTX | PptxGenJS | 텍스트·이미지 기반 PPTX 생성 |
| PDF | pdf-lib | 각 슬라이드의 렌더링 이미지를 한 페이지에 배치 |
| 검증 | 단위 테스트 도구 + Playwright + 실제 PowerPoint | 데이터 계약·사용자 흐름·출력물 모양을 각각 확인 |

위 라이브러리는 후보 선택이며 설치나 성능 검증 결과가 아니다. 2단계에서 호환 버전, 라이선스, 번들 크기를 기록하고 잠금 파일로 고정한다.

공식 문서 근거: [React Konva](https://konvajs.org/docs/react/index.html)는 React에서 캔버스 요소와 이벤트를 연결한다. [Konva 글씨 입력 예제](https://konvajs.org/docs/sandbox/Editable_Text.html)는 HTML 입력 요소를 이용하는 방식을 제시한다. [PptxGenJS](https://gitbrent.github.io/PptxGenJS/)는 브라우저 PPTX 생성과 텍스트·이미지 요소를 제공한다. [pdf-lib](https://pdf-lib.js.org/)는 브라우저에서 PDF 생성과 이미지 삽입을 지원한다. 이 사실이 우리 앱의 한글·출력 호환성을 보장하는 것은 아니다.

## 5. 데이터 구조와 변경 경로

문서 원본은 캔버스 라이브러리의 직렬화 결과와 분리한다. 문서 저장소만 원본을 변경할 수 있으며, 캔버스·미리보기·출력은 원본을 읽는다. 드래그 중의 임시 위치는 화면에서 관리하고 드래그 종료 시 한 번의 문서 명령으로 확정한다.

### 저장 객체

| 객체 | 필수 정보 |
|---|---|
| Project | schemaVersion, id, title, revision, createdAt, updatedAt, width, height, slides, assetManifest |
| Slide | id, background, elements 배열 |
| Background | 단색 또는 이미지 종류, 색 또는 assetId, 가운데 채우기 규칙 |
| 공통 요소 | id, type, x, y, width, height |
| TextElement | 공통 요소 + text, fontFamily, fontSize, color, bold, align, lineHeight |
| ImageElement | 공통 요소 + assetId. 첫 버전은 전체 사진 비율 유지 |
| StrokeElement | 공통 요소 + 요소 내부의 points, color, strokeWidth |
| Asset | id, mime, 원본 파일명, 픽셀 크기, 바이트 크기, 콘텐츠 해시, 바이너리 저장 참조 |

elements 배열 앞쪽이 뒤에 그려지고 뒤쪽이 앞에 그려진다. 별도 zIndex를 중복 저장하지 않는다. 선택 상태·활성 도구·화면 확대율·object URL·미리보기 캐시는 원본에 저장하지 않는다. 슬라이드 복사는 요소 ID를 새로 만들되 사진 자산은 공유한다.

### 좌표와 크기

- 논리 슬라이드 크기는 1280 × 720이다. 표시 배율은 화면 크기와 별개로 계산한다.
- 화면 입력은 캔버스 오프셋과 배율을 역변환한 뒤 논리 좌표로 기록한다. 브라우저 기기 픽셀 비율을 원본 좌표에 섞지 않는다.
- PPTX는 13⅓ × 7.5 inch, PDF는 960 × 540 point를 기준으로 한다. 좌표 변환은 inch = 논리 px / 96, point = 논리 px × 0.75다.
- 글씨 크기도 논리 px로 기록하고 PPTX 글씨 크기로 변환할 때 point 규칙을 적용한다. 실제 줄바꿈과 폰트 메트릭은 별도 검증한다.
- 첫 버전은 요소가 슬라이드 바깥으로 완전히 사라지지 않게 이동 범위를 제한한다. 선택 테두리는 출력에서 제외한다.

### 모듈 계약

| 계약 | 입력과 결과 |
|---|---|
| dispatch(command) | 요소 추가·수정·삭제, 순서·배경 변경 등의 명령 → 새 revision |
| importAsset(file) | 파일 → 검증·정규화한 Asset 또는 사용자에게 보여줄 오류 |
| renderSlide(snapshot, slideId, options) | 문서 스냅샷과 자산 → 화면 또는 출력 이미지 |
| saveProject(snapshot) | 문서와 참조 자산 → 저장된 revision 또는 실패 |
| serializeProject / deserializeProject | 문서·자산 ↔ 원본 파일. 읽을 때 버전·참조 검사 |
| exportPptx / exportPdf | 불변 스냅샷·자산 resolver·출력 옵션 → Blob과 경고 목록 |

명령은 검증된 변경을 한 번에 적용하고 되돌리기 정보를 남긴다. 이동 1회와 획 1개를 각각 취소 1회로 처리한다. 글씨는 입력 세션 또는 정해진 편집 묶음으로 취소한다. 실제 경계는 1단계 계약에서 정한다. 최초 목표는 최대 100개 명령이며 이미지 바이너리는 복제하지 않는다.

## 6. 저장·복구 설계

문서 JSON과 이미지 바이너리를 분리한다. 자동 저장은 마지막 변경 후 1초를 기본값으로 하고, 변경이 계속되면 최대 5초 간격으로 저장하도록 설계한다. 이 수치는 구현 목표이며 성능 측정 후 조정할 수 있다.

저장 상태는 변경 있음 → 저장 중 → 저장됨 또는 저장 실패다. 저장 작업은 순서대로 처리하며 완료된 revision이 현재 revision과 같을 때만 저장됨으로 표시한다. 이전 저장 요청이 늦게 완료되어 새 작업을 덮어쓰지 않게 한다.

IndexedDB의 문서·자산 갱신은 가능한 범위에서 한 트랜잭션으로 처리한다. 저장 실패 시 편집 내용을 메모리에 유지하고 원본 다운로드를 안내한다. 탭 종료 이벤트에만 저장을 의존하지 않는다. 같은 작품을 여러 탭에서 열었을 때는 첫 버전에서 한 탭만 편집하도록 잠금·충돌 감지를 설계한다.

원본 파일 확장자는 .canvacraft로 제안한다. 내부는 manifest.json, project.json, assets/로 구성한다. 읽을 때 파일 수·압축 해제 크기·스키마 버전·자산 참조를 검사한다. 더 새로운 스키마는 임의 변환하지 않고 안내한다. 오류가 있는 파일을 열다가 현재 작품을 잃지 않도록 새 문서 검증 완료 후 교체한다.

자산 삭제는 현재 문서와 실행 취소 기록에서 참조하지 않을 때만 수행한다. 작업 원본을 다시 열었을 때 실행 취소 기록까지 복원하는 기능은 첫 버전에서 제외한다.

## 7. PPTX·PDF 내보내기 설계

### 기본 PPTX: 수정 가능한 글씨·사진

| 원본 요소 | PPTX 변환 | 수정 범위 |
|---|---|---|
| 단색 배경 | 슬라이드 배경 | 배경 변경 가능 |
| 사진 배경 | 슬라이드 뒤쪽 이미지 | 이미지 요소로 수정 가능 |
| 사진 | 이미지 요소 | 이동·크기 변경·교체 가능 |
| 글씨 | 텍스트 상자 | 내용·서식 수정 가능 |
| 손그림 | 획별 또는 인접한 획 묶음의 투명 PNG | 이미지 이동·크기 변경 가능, 획 자체 편집 불가 |

손그림 전체를 한 장으로 합치면 사진 앞뒤에 있는 획의 순서가 깨질 수 있다. 따라서 elements 순서를 유지하며 연속된 획만 묶거나 획별 이미지로 출력한다. 예를 들어 사진 → 그림 → 글씨 → 그림 순서는 그대로 보존한다.

글씨는 상자 여백, 줄 간격, 크기, 굵기, 정렬을 명시적으로 변환한다. 출력 시 자동 맞춤에만 의존하지 않는다. 웹에서 사용하는 폰트가 수신 PC에 없으면 글꼴과 줄바꿈이 달라질 수 있으며, 웹폰트 탑재가 PPTX 폰트 포함을 뜻하지 않는다. 2단계에서 사용할 한글 폰트와 대체 규칙을 확정한다.

보조 옵션으로 슬라이드 전체를 이미지로 넣는 ‘모양 그대로 PPT’를 제공한다. 이 모드는 글씨와 사진의 개별 편집이 불가능하다는 설명을 다운로드 화면에 표시한다. 기본 모드의 한계를 숨기고 자동으로 이미지 모드로 바꾸지 않는다.

### PDF

첫 버전은 렌더러로 슬라이드를 이미지화하고 PDF 각 페이지에 배치한다. 출력 이미지는 우선 2560 × 1440을 목표로 한다. 글씨 검색·선택과 벡터 확대 품질은 제공하지 않는다. 향후 벡터 PDF를 별도 과제로 확장할 수 있다.

### 공통 출력 절차

진행 중 입력 확정 → 불변 스냅샷 생성 → 폰트·사진 로딩 확인 → 슬라이드별 처리 → Blob 생성 → 다운로드 순서다. 내보내기 중 편집한 내용은 해당 파일에 섞지 않는다. 진행률·취소·실패 안내를 제공하고, 큰 문서는 한 장씩 처리해 중간 이미지 메모리를 해제한다. 누락된 자산을 조용히 빈칸으로 내보내지 않는다.

## 8. 10단계 상세 실행 계획

### Phase 1. 범위와 공통 계약 확정

- 선행 조건: 이 설계안 공유.
- 작업: 문서 스키마, 명령 종류, 저장·출력 계약, 모듈 경계를 정리한다.
- 작업: 화면 흐름, 도구 상태 전환, 어린이용 문구, 키보드·터치 동작을 정리한다.
- 산출물: 기존 개발 계획과 docs/contracts.md 보완. 별도 담당 문서는 필수가 아니다.
- 완료 기준: 모든 포함 기능이 데이터 필드·사용자 조작·출력 규칙에 연결되고, 단일 상태 소유자와 모듈 경계가 정리되어 있다.
- 인계: 이어받는 AI도 같은 예제 문서와 명령 이름을 사용한다. 구현 코드는 다음 단계부터 작성한다.

### Phase 2. 실패 위험이 큰 기술부터 검증

- 선행 조건: Phase 1 계약.
- 작업: 최소 캔버스에서 한글 textarea 입력, 사진 이동, 터치 획 입력을 시험한다.
- 작업: 같은 예제 데이터를 PPTX·PDF로 내보내는 작은 시험 코드를 만든다.
- 시험 내용: ‘우리 가족 소개’, 긴 한글 문장, 명시적 줄바꿈, 굵게, 투명 PNG, 사진 앞뒤의 획, 폰트가 없는 PC의 대체 표시.
- 산출물: 시험 코드, 예제 원본·출력물, 브라우저·PowerPoint 버전, 스크린샷과 제한 사항, 의존성 버전 결정.
- 완료 기준: 브라우저 한글 조합이 유지되고 PPTX를 실제 PowerPoint에서 열어 텍스트 수정·사진 이동을 확인한다. PDF도 실제 뷰어로 확인한다.
- 중단 조건: 출력만 성공하고 실제 앱에서 열어보지 못했으면 출력 호환성은 미검증으로 남긴다. 구조적 문제가 발견되면 Phase 1 계약을 먼저 수정한다.

### Phase 3. 앱 기반과 상태 변경 구조

- 선행 조건: Phase 2의 기술 선택.
- 작업: 프로젝트 구성, 타입, 단일 문서 저장소, 명령 처리, 취소·다시 실행을 만든다.
- 작업: 도구 영역·슬라이드 목록·캔버스 틀, 문서 읽기 렌더러를 만든다.
- 산출물: 실행 가능한 기본 앱, 명령 계약 테스트, 공통 샘플 문서.
- 완료 기준: 하나의 명령으로 문서를 변경하면 화면에 반영되고 취소 시 원래 상태로 돌아온다. 렌더러 내부에 별도 영구 문서 상태가 없다.

### Phase 4. 슬라이드와 요소 기본 조작

- 선행 조건: Phase 3.
- 작업: 새 장·복사·삭제·순서 변경, 요소 선택·이동·비율 유지 크기 변경, 앞뒤 이동을 구현한다.
- 작업: 요소 ID·슬라이드 ID, 명령의 경계값과 취소 동작을 검토한다.
- 산출물: 슬라이드 목록, 선택 조작, 좌표 변환 함수와 검증 사례.
- 완료 기준: 표시 배율 50%·100%·150%에서도 의도한 위치로 이동한다. 슬라이드 복사 후 한쪽 편집이 다른 쪽 요소를 바꾸지 않는다. 드래그 한 번은 취소 한 번이다.

### Phase 5. 사진과 배경

- 선행 조건: Phase 4, 자산 계약 확정.
- 작업: 파일 검사, 방향·크기 정규화, 자산 저장, 오류 반환을 구현한다.
- 작업: 파일 선택·드롭·붙여넣기와 배경 선택 화면을 연결한다.
- 산출물: 자산 입력 모듈, 사진·배경 도구, 정상·손상·초대형 파일 사례.
- 완료 기준: 세 가지 입력 경로에서 같은 사진을 사용할 수 있다. 붙여넣기가 허용되지 않는 환경에서는 파일 선택을 안내한다. 배경을 바꿔도 글씨와 사진이 유지된다. 손상 파일은 기존 작업을 훼손하지 않는다.

### Phase 6. 글씨와 한글 입력

- 선행 조건: Phase 4, Phase 2 한글 검증 결과.
- 작업: textarea 위치·크기 동기화, 조합 이벤트 처리, 서식 도구, 입력 확정·취소를 구현한다.
- 작업: 출력에 필요한 텍스트 필드와 저장 데이터 일치 여부를 검토한다.
- 산출물: 글씨 편집기, IME 수동 시험 절차, 줄바꿈 샘플.
- 완료 기준: 한글 조합 중 Enter·Escape·슬라이드 전환으로 글자가 중복되거나 사라지지 않는다. 입력 중 Delete가 글씨 상자를 삭제하지 않는다. 화면 확대 후에도 입력 위치가 일치한다.

### Phase 7. 손그림과 획 지우기

- 선행 조건: Phase 4, Phase 6 모드 전환 계약.
- 작업: 포인터 입력, 펜 색·굵기, 획 선택·이동·지우기, 입력 중 화면 스크롤 제어를 구현한다.
- 작업: 획 저장 형식과 출력 순서를 검토한다.
- 산출물: 그리기 도구, 획 데이터, 터치·취소 사례.
- 완료 기준: 손가락이나 펜이 캔버스를 벗어나거나 pointercancel이 발생해도 그리기 상태가 고정되지 않는다. 획 지우기는 사진을 지우지 않는다. 획 한 개의 추가·삭제를 한 번에 되돌린다.

### Phase 8. 자동 저장과 작업 원본

- 선행 조건: Phase 5~7 데이터 구조 안정화. 저장 어댑터 구현은 Phase 3 이후 별도 작업 가능.
- 작업: IndexedDB, revision별 저장, 원본 ZIP 읽기·쓰기, 버전 검사, 복구·다중 탭 충돌 처리를 구현한다.
- 작업: 저장 상태·실패·복구 화면을 연결한다.
- 산출물: 원본 파일 형식 명세, 저장·열기 기능, 손상 파일과 저장 실패 시험.
- 완료 기준: 사진·글씨·손그림이 섞인 작품을 재시작·원본 다운로드·새 브라우저 프로필에서 열기 방식으로 복원한다. 저장 실패 후에도 원본을 내려받을 수 있다. 오래된 저장 응답이 새 revision을 덮어쓰지 않는다.

### Phase 9. PPTX·PDF·발표 통합

- 선행 조건: Phase 5~8, Phase 2 출력 검증 결과.
- 작업: 정식 출력 변환기, 기본 PPTX·모양 유지 PPTX·PDF, 진행률·취소를 구현한다.
- 작업: 다운로드 옵션, 경고 표시, 전체 화면 발표·이전·다음 이동·종료를 구현한다.
- 산출물: 각 출력 형식의 예제, 실제 PowerPoint·PDF 확인 기록, 알려진 폰트 제약.
- 완료 기준: 배경·사진·글씨·획 순서가 맞고 편집용 PPTX의 글씨를 수정할 수 있다. PDF 페이지 수와 순서가 원본과 같다. 출력 중 편집은 출력 스냅샷을 바꾸지 않는다. 취소 후 재시도가 가능하다.

### Phase 10. 통합 품질과 출시 준비

- 선행 조건: Phase 9까지 기능 통합.
- 작업: 저장·출력 오류, 큰 문서, 자산 누락, 스키마 검증, 빌드·배포 절차를 점검한다.
- 작업: 어린이 작업 흐름, 키보드·터치, 화면 크기, 안내 문구, 발표 동작을 점검한다.
- 산출물: 통합 시험 보고서, 미해결 항목, 사용 설명, 정적 배포 패키지와 되돌리는 절차.
- 완료 기준: 아래 대표 시나리오를 실제 환경에서 통과한다. 가능하면 보호자·교사 입회하에 어린이 3명 이상이 조작하는 모습을 관찰하고 막힌 지점을 수정한다. 참여자를 구하지 못하면 사용성 검증 미실시로 기록한다.
- 공개 배포는 별도 실행 작업이다. 이 설계 문서 작성이나 배포 패키지 준비를 공개 배포 완료로 기록하지 않는다.

## 9. AI를 바꿔 이어서 개발하는 방식

Codex와 Claude의 고정 담당, 파일 소유권, 병렬 작업은 두지 않는다. 현재 작업하는 AI가 화면·데이터·저장·출력 중 다음에 필요한 부분을 모두 구현한다. 10개 Phase와 기술 계약은 유지한다.

토큰이 부족하거나 사용자가 AI를 바꿀 때, docs/PROGRESS.md 한 파일에 다음 내용만 갱신한다. 개발 착수 때 만들며 별도 담당 문서는 작성하지 않는다.

- 현재 Phase와 완료한 작업
- 수정한 주요 파일과 아직 끝내지 못한 작업
- 실제 실행한 검증 결과와 실패·미검증 항목
- 다음에 바로 할 작업, 진행을 막는 문제가 있으면 그 내용
- Git을 사용한다면 현재 브랜치·커밋과 미커밋 변경 사항

이어받는 AI는 진행 기록과 실제 파일 상태를 확인하고 중단 지점부터 계속한다. 설계를 처음부터 다시 작성하거나 이전 검증을 이유 없이 반복하지 않는다. AI 교체만을 위해 별도 브랜치·worktree·통합 담당을 만들지 않는다. 같은 작업 공간에서 두 AI가 동시에 수정하지 않는다.

## 10. 검증 기준과 성능 목표

아래 수치는 초기 설계 목표다. Phase 2에서 기준 기기의 CPU·메모리·OS·브라우저·PowerPoint 버전을 기록하고 측정 후 조정한다.

| 항목 | 초기 목표와 확인 방법 |
|---|---|
| 대표 문서 | 20장, 장당 요소 50개까지의 혼합 문서로 기본 동작 시험 |
| 사진 입력 | 파일당 20MB·40MP를 초기 상한으로 검토하고 디코딩 전후 검사. 내부 최대 긴 변 2560px 목표 |
| 조작 반응 | 기준 문서에서 선택·이동 반응 100ms 이내 목표. 실제 브라우저 측정 |
| 그리기 | 기준 기기에서 눈에 띄는 입력 누락 없이 지속 입력. 포인터·렌더 시간 측정 |
| 저장 | 변경 완료 후 1초 예약, 저장 완료 후에만 완료 표시. 지연·실패를 주입해 확인 |
| 출력 | 20장 기준 30초 이내 목표. 진행률 제공, 장별 처리로 메모리 사용 제한 |
| 시각 비교 | 줄바꿈·요소 겹침·잘림·순서 오류를 필수 수정으로 판정. 렌더러별 글자 가장자리 차이는 구분 |

대표 사용자 시나리오:

1. 새 작품을 만들고 제목을 한글로 입력한다.
2. 배경을 고르고 사진을 붙여넣어 크기·위치를 바꾼다.
3. 두 줄짜리 글씨와 손그림을 넣고 그림 한 획을 지웠다가 되돌린다.
4. 슬라이드를 복사하고 두 번째 장의 글씨만 바꾼 뒤 순서를 바꾼다.
5. 브라우저를 다시 열어 복원을 확인하고 원본 파일을 다른 프로필에서 연다.
6. PPTX에서 글씨 수정과 사진 이동을 확인하고 PDF의 페이지·모양을 비교한다.
7. 손상 사진, 저장 용량 부족, 누락 자산, 긴 한글 문장, 출력 취소를 각각 시험한다.

단위 테스트는 좌표 변환·명령 취소·원본 왕복·버전 검사·출력 요소 변환을 확인한다. 브라우저 테스트는 실제 사용자 흐름을 확인한다. IME와 실제 PowerPoint 표시 결과는 자동 테스트만으로 통과 처리하지 않는다.

## 11. 추정 일정과 착수 순서

Phase 1: 1~2일, Phase 2: 2~4일, Phase 3: 2~3일, Phase 4: 2~3일, Phase 5: 2~3일, Phase 6: 2~4일, Phase 7: 2~3일, Phase 8: 2~4일, Phase 9: 3~5일, Phase 10: 3~5일을 초기 작업량으로 잡는다. 단계별 단순 합계는 21~36 작업일이며 확정 일정이 아니다. AI 교대는 병렬 개발이 아니므로 일정 단축 배수를 적용하지 않는다. 실제 일정은 Phase 2 결과와 기기 검증에 필요한 시간으로 다시 산정한다.
