# 애니메이션 A2 기술 검증 결과

측정일: 2026-11-10. 기준 문서는 [animation-contracts.md](animation-contracts.md) §9의 A2 행과 [ANIMATION_PLAN.md](ANIMATION_PLAN.md) §8 A2다.

## 3분 요약

**결론.** 계획한 구조(메인 스레드가 `renderSlide`로 장을 그려 한 장씩 넘기고 Worker가 인코딩)로 진행한다. 중단 조건에 걸린 항목은 없다. 출력 방식은 **24fps 반복 방식으로 확정**한다.

| 항목 | 목표 | 측정(개발 PC) | 판단 |
|---|---|---|---|
| 100장 그리기 합계(출력 1.5배) | 30초 이내(넘으면 중단 조건) | 그림 문서 0.2~0.9초, 사진 문서 9.6~10.6초 | 통과 |
| 100장 내보내기 전체(16.7초 영상) | 60초 이내 | 그림 문서 1.9~2.8초, 사진 문서 10.6~12.1초 | 통과 |
| 가장 긴 작품(4,800프레임, 200초 영상) | — | 사진 문서 MP4 23.5~24.6초, WebM 27.1~28.0초 | 참고 |
| 출력 정확도 | 프레임 수·길이·장 전환이 계약 §3 식과 일치 | 브라우저 3종 × 출력 7종 모두 일치 | 통과 |
| 내보내기 메모리 | 탭 1GB 이내 | 렌더러 프로세스 최대 657MB, GPU 프로세스 최대 463MB | 통과(아래 한계 참고) |
| 재생 캐시 100장 만들기 | — | 그림 문서 0.2~0.5초, 사진 문서 약 10초 | 주의: 사진이 많은 작품은 첫 재생이 밀린다 |

**확인하지 못한 것.** RAM 8GB PC, Windows 미디어 플레이어 재생, YouTube 업로드, 양파 껍질을 켠 채 끄는 동안의 실제 프레임 간격(제품 화면이 생기는 A5에서 잰다), 메인 스레드가 실제로 멈추는 시간(아래 수치는 기다린 시간을 포함한 벽시계 시간이다).

**알게 된 것.** 장을 그리는 시간의 대부분은 사진 해독이다. 그림·스티커·글씨만 있는 장은 2~10ms, 큰 사진 4장이 든 장은 약 100ms다. 같은 사진을 여러 장이 써도 `renderSlide`는 장마다 다시 해독한다. 사진 해독 결과를 장 사이에 나눠 쓰면 사진 문서의 시간이 크게 줄겠지만 슬라이드 렌더 코드를 고쳐야 해서 첫 버전에서는 하지 않는다(후속 후보).

## 2. 장 그리기 시간

100장을 차례로 그린 벽시계 시간이다(ms). 첫 장은 글꼴·해독기 준비를 포함하므로 한 번 미리 그린 뒤에 쟀다.

| 문서 | 배율(쓰임) | Chromium 평균 / p95 / 합계 | Chrome 평균 / p95 / 합계 | Edge 평균 / p95 / 합계 |
|---|---|---|---|---|
| 그림 | 1.5배(출력) | 9.0 / 10.2 / 904 | 2.3 / 3.0 / 228 | 2.2 / 3.0 / 216 |
| 그림 | 1배(양파 껍질) | 6.5 / 7.5 / 649 | 1.9 / 2.4 / 191 | 2.1 / 2.7 / 207 |
| 그림 | 0.5배(재생 캐시) | 5.4 / 6.5 / 540 | 2.2 / 2.8 / 216 | 5.4 / 2.6 / 545 |
| 사진 | 1.5배(출력) | 97.8 / 101.5 / 9,780 | 105.6 / 117.9 / 10,562 | 99.1 / 103.4 / 9,908 |
| 사진 | 1배(양파 껍질) | 93.1 / 97.5 / 9,308 | 103.3 / 108.6 / 10,325 | 102.2 / 106.9 / 10,225 |
| 사진 | 0.5배(재생 캐시) | 92.2 / 96.4 / 9,223 | 101.9 / 108.9 / 10,187 | 101.4 / 105.0 / 10,140 |

- 사진 문서는 배율과 관계없이 장당 약 100ms다. 시간의 대부분이 사진 4장의 해독이고 그리는 크기는 영향이 작다는 뜻이다.
- 그린 캔버스를 `ImageBitmap`으로 바꾸는 시간은 장당 0.1~0.4ms(그림), 1.3~10.5ms(사진)였다.
- Edge 그림 문서 0.5배의 평균이 p95보다 큰 것은 한 장이 342ms 걸렸기 때문이다(나머지는 2~3ms). 원인은 확인하지 않았다.
- 양파 껍질은 장을 옮길 때 앞 장을 1배로 한 번 그린다. 그림 장은 2~8ms, 사진 장은 약 100ms 뒤에 깔린다.

## 3. 내보내기

100장을 그려 넘기고 인코딩해 파일을 닫을 때까지의 시간이다. "그리기"는 메인 스레드의 `renderSlide` 합계, "인코딩"은 Worker가 그림을 받아 프레임을 넣은 시간의 합계다.

| 출력 | 브라우저 | 전체(초) | 그리기(초) | 인코딩(초) | 파일(MB) | 렌더러 / GPU 최대(MB) |
|---|---|---|---|---|---|---|
| 그림 400프레임 MP4 반복 | Chromium / Chrome / Edge | 1.9 / 2.8 / 2.5 | 1.0 / 0.2 / 0.2 | 0.6 / 1.8 / 1.7 | 14.1 / 13.8 / 13.8 | — / 207·214 / 177·128 |

| 그림 400프레임 WebM 반복 | Chromium / Chrome / Edge | 2.6 / 2.3 / 2.9 | 1.1 / 0.2 / 0.3 | 1.3 / 1.9 / 2.5 | 16.1 / 15.8 / 15.8 | — / 641·414 / 657·368 |
| 사진 4,800프레임 MP4 반복 | Chromium / Chrome / Edge | 23.7 / 24.6 / 23.5 | 10.1 / 9.8 / 9.7 | 13.2 / 13.8 / 12.7 | 75.3 / 200.5 / 200.5 | — / 492·441 / 504·437 |
| 사진 4,800프레임 WebM 반복 | Chromium / Chrome / Edge | 28.0 / 27.1 / 27.2 | 11.2 / 10.2 / 10.1 | 16.4 / 15.9 / 16.1 | 150.4 / 134.7 / 134.7 | — / 580·409 / 582·415 |
| 그림 400프레임 MP4 가변 | Chromium / Chrome / Edge | 1.6 / 1.4 / 1.5 | 1.0 / 0.2 / 0.3 | 0.3 / 1.0 / 1.0 | 4.7 / 5.6 / 5.6 | — / 394·393 / 452·415 |

- 400프레임은 초당 6장·100장(16.7초 영상), 4,800프레임은 초당 2장·모든 장 4배(200초 영상)다.
- 메인 스레드가 한 장을 그리는 가장 긴 시간은 그림 문서 15ms, 사진 문서 129ms였다(벽시계 시간). 장 사이에서 화면이 갱신되므로 진행률은 장마다 바뀐다.
- headless Chromium의 프로세스별 메모리는 표본기가 렌더러를 구분하지 못해 비웠다.
- 메모리 수치는 프로세스 전체의 최대값이고 내보내기를 시작하기 전 값을 빼지 않았다. 브라우저 전체 합계 최대는 1,398MB(Chrome, WebM)였고 첫 내보내기 때는 611~725MB였다. 뒤로 갈수록 커진 것은 같은 탭에서 일곱 번을 이어 돌렸기 때문일 수 있으며 따로 가려 보지 않았다.

### 출력 파일 확인

만든 파일을 다시 해독해 계약 §3의 식과 견줬다(브라우저 3종 × 출력 7종).

| 확인 | 결과 |
|---|---|
| 패킷 수 | 반복 방식은 전체 프레임 수(400·4,800), 가변 방식은 장 수(100)와 같다 |
| 길이 | 16.67~16.68초, 200.0초(오차 0.1초 이내) |
| 장 전환(그림 문서) | 장 1·2·50·99의 첫 프레임과 그 직전 프레임을 해독해 배경색으로 장을 판별했다. 직전 프레임은 앞 장, 첫 프레임은 그 장이었다(반복·가변 모두) |
| 소리 트랙 | MP4는 AAC, WebM은 Opus 무음 트랙이 있다 |
| Chrome `<video>` 재생 | 60MB 이하 파일은 모두 열렸고 길이가 맞았으며 1.4초 재생 동안 버린 프레임 0, 가운데로 건너뛰기 성공. 사진 4,800프레임 파일(75~200MB)은 크기 때문에 내려받지 않아 재생하지 않았다 |

## 4. 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 그리기 위치 | 메인 스레드 `renderSlide` 1.5배, 인코딩은 Worker(계획대로) | 100장 그리기 합계가 가장 나쁜 경우 10.6초로 중단 조건(30초)의 3분의 1이다 |
| 출력 방식 | **24fps 반복**(계약 §3 확정) | 프레임 수·길이·장 전환이 정확하고 YouTube 권장 형식(고정 프레임률)이다. 가변 방식은 같은 그림 문서 400프레임에서 파일이 2.5~3배 작았고(13.8~14.1MB → 4.7~5.6MB) 길게 보이는 장이 많을수록 차이가 커지지만, 2초에 한 프레임인 MP4를 Windows 미디어 플레이어 등이 고르게 재생하는지 확인하지 않았다 |
| 비트레이트 | 영상 계약과 같은 8Mbps 유지 | 대표 작품(100장, 16.7초)이 14~19MB다. 가장 긴 작품(200초)은 하드웨어 인코더에서 200MB까지 나온다. 정지 그림이 대부분이라 낮춰도 될 가능성이 높지만 화질을 견줘 보지 않았다 |
| 한 번에 넘기는 그림 | 1장(계획대로) | 렌더러 최대 657MB로 목표 안이다 |
| 재생 캐시 | 640×360 비트맵을 장마다 만들어 쥔다(계획대로). 사진이 많은 작품은 캐시가 다 차기 전에 재생이 시작되므로 그림이 없는 장은 전 그림을 유지한다 | 그림 문서는 100장이 0.5초 안에 준비된다. 사진 문서는 장당 100ms라 초당 8장 이상에서는 첫 바퀴가 밀린다 |
| 양파 껍질 | 앞 장을 1배로 그려 배경 레이어에 깐다(계획대로). 끄는 동안의 프레임 간격은 A5에서 제품 화면으로 잰다 | `SlideCanvas`는 끌리는 요소만 따로 그리므로(코드 확인) 깔아 둔 그림은 끄는 동안 다시 그려지지 않는다. 그림 한 장을 투명도 0.35로 까는 비용은 소프트웨어 캔버스에서 0.5ms였다. GPU 캔버스의 5.9~7.4ms는 결과를 읽어 오는 시간이 포함된 값이라 화면 그리기 비용으로 볼 수 없다 |

## 5. 미검증과 후속 후보

| 항목 | 상태 |
|---|---|
| RAM 8GB PC | 측정하지 않았다. 영상 V2에서 그래픽 가속 없는 가상 PC의 인코딩 메모리가 목표를 넘은 일이 있다(보류 중). 애니메이션은 조각 해독이 없어 부담이 덜할 것으로 보지만 추정이다 |
| Windows 미디어 플레이어·YouTube | 사람 확인이 필요하다. `artifacts/animation-phase2/`의 `drawing-400-chrome.mp4`(반복)와 `drawing-400-variable-chrome.mp4`(가변)를 열어 보면 두 방식을 견줄 수 있다 |
| 메인 스레드가 실제로 멈추는 시간 | 벽시계 시간만 쟀다. 사진 해독을 기다리는 동안은 화면이 멈추지 않으므로 실제 멈춤은 이보다 짧을 것이다 |
| 실제 사진 | 합성 사진만 썼다 |
| 음악을 섞은 출력 | 무음 트랙으로만 쟀다. 음악 섞기는 영상 편집기에서 쓰는 코드(`audioMix.ts`)이고 A6에서 출력 파일의 소리를 확인한다 |
| 사진 해독 나눠 쓰기(후속 후보) | 같은 사진을 쓰는 장이 많은 작품에서 내보내기·재생 준비 시간을 줄일 수 있다. `renderSlide`에 선택 인자를 더해야 한다 |
| 가변 길이 출력·낮은 비트레이트(후속 후보) | 파일 크기를 줄인다. 실제 플레이어 재생과 화질 확인이 먼저다 |
